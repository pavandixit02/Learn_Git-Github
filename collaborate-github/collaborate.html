1. Collaborate on GitHub kya hota hai?

GitHub Collaboration ka matlab hai ki multiple developers/team members ek shared GitHub repository ke around code ko develop, review, discuss aur merge karte hain.

Simple idea: Ek developer apne branch par change karta hai → GitHub par push karta hai → Pull Request banata hai → team review karti hai → approved changes target branch me merge hote hain.

Collaboration sirf code upload karna nahi hai. Isme version control + branch strategy + code review + permissions + communication + CI/CD sab involved ho sakte hain.

5. GitHub Repository Access & Permissions

Team collaboration me har person ko same level ka access dena zaroori nahi hota.

Access ConceptMeaning
ReadRepository ko dekh/clone karna.
TriageIssues/discussions ko manage karne jaisi limited collaboration capabilities.
WriteRepository me changes push karne ki capability, subject to branch rules.
MaintainRepository management ki broader capabilities, sensitive administration ke bina.

Important: Actual permissions organization/repository configuration aur branch protection rules par depend karte hain. Production branches ko controlled access dena common best practice hai.

Collaborator invite ka high-level process

  1. GitHub repository open karo.
  2. Repository settings/access area me jao.
  3. Team member ko invite karo.
  4. Required permission level assign karo.
  5. Member invite accept karta hai.
  6. Uske baad configured permissions ke according repository access milta hai.

8. Pull Request (PR) kya hota hai?

Pull Request GitHub par ek proposal hota hai jisme aap apni branch ke changes ko target branch me integrate/review karne ke liye submit karte ho.

Example:

feature/login  ───────►  main
                  Pull Request

PR ka typical lifecycle

  1. Feature branch create.
  2. Code changes.
  3. Commits create.
  4. Branch GitHub par push.
  5. Pull Request open.
  6. Title + description add.
  7. Reviewers assign.
  8. Automated CI checks run.
  9. Reviewer comments/suggestions de sakta hai.
  10. Developer requested changes karta hai.
  11. Checks pass hone aur approval ke baad merge.

Good PR title

Add JWT authentication for user login

Good PR description structure

## What
Added JWT-based login authentication.

## Why
Users need secure authentication.

## Changes
- Added login endpoint
- Added JWT generation
- Added authentication middleware

## Testing
- Tested valid login
- Tested invalid credentials
- Tested expired token

## Notes
No database schema changes.

9. Code Review

Code review ka purpose sirf “code correct hai ya nahi” check karna nahi, balki maintainability, security, readability, tests aur project standards ko review karna bhi hai.

🔍 Correctness

Kya expected behavior implement hua?

🔐 Security

Kya secrets, injection, auth issues ya unsafe patterns hain?

🧪 Testing

Kya relevant tests add/update kiye gaye?

📖 Readability

Kya code understandable aur maintainable hai?

⚡ Performance

Kya unnecessary expensive operations hain?

🏗️ Architecture

Kya change existing design ke saath fit hota hai?

Review feedback ka healthy style

Good: “Could we validate the input before calling the database? This would prevent invalid requests from reaching the query layer.”
Avoid: Personal attacks ya vague comments jaise “This code is bad.”

11. Collaboration me Merge Conflict

Jab do changes same file ke overlapping lines/areas ko incompatible tarike se modify karte hain, Git automatic merge nahi kar pata aur conflict report kar sakta hai.

Example

<<<<<<< HEAD
Hello from main
=======
Hello from feature/login
>>>>>>> feature/login

Conflict resolution workflow

# 1. Identify conflicts
git status

# 2. Open conflicted files
# 3. Remove conflict markers and choose/fix final content

# 4. Stage resolved files
git add <file>

# 5. Complete merge if doing a merge
git commit

# or continue rebase if you were rebasing
git rebase --continue
Never blindly accept “ours” or “theirs”. Pehle understand karo ki dono changes kya kar rahe hain aur final code me kya behavior required hai.

PR conflict ko locally resolve karne ka common approach

git fetch origin
git switch feature/login

# Update your understanding of target branch
git merge origin/main

# Resolve conflicts
git status

git add .
git commit

git push

Alternative team policy ke according rebase workflow bhi use ho sakta hai:

git fetch origin
git switch feature/login
git rebase origin/main

# Resolve conflicts
git add .
git rebase --continue

git push --force-with-lease
Force push caution: Rebase ke baad branch history rewrite ho sakti hai. Shared branch par force push avoid karo. Personal feature branch par bhi generally --force-with-lease ko plain --force se prefer kiya jata hai.

Fork workflow commands

# Clone your fork
git clone git@github.com:YOUR-USERNAME/project.git
cd project

# Add original repository as upstream
git remote add upstream https://github.com/ORIGINAL-OWNER/project.git

# Check remotes
git remote -v

# Update from original project
git fetch upstream

# Create feature branch from updated main
git switch main
git merge upstream/main

git switch -c feature/my-change

# Work + commit
git add .
git commit -m "Add my improvement"

# Push to your fork
git push -u origin feature/my-change

Uske baad GitHub par apne fork se original repository ke target branch ke against Pull Request open karte ho.

16. Protected Branches & Rules

Teams important branches par rules configure kar sakti hain. Exact available controls repository plan/settings par depend karte hain.

  • Direct pushes restrict karna.
  • Pull Request require karna.
  • Required reviews configure karna.
  • Required status/CI checks configure karna.
  • Conversation resolution requirements configure karna.
  • Branch update requirements configure karna.
  • Force pushes/deletions ko restrict karna.
Professional principle: Stable/production branches ko controlled integration point banana aur feature work ko PR ke through integrate karna accidental breakage ka risk reduce kar sakta hai.

19. Collaboration Security

🔑 Never commit secrets

API keys, passwords, private keys aur tokens repository me commit mat karo.

🛡️ Least privilege

Users ko required permission se zyada access na dena.

🔎 Review dependencies

Third-party dependencies aur workflow changes carefully review karo.

🤖 Protect CI/CD

Untrusted PR code ko sensitive deployment credentials tak unnecessary access mat do.

.gitignore example

.env
.env.*
*.pem
*.key
node_modules/
dist/
__pycache__/
Important: Sirf .gitignore me secret add karna enough nahi hai agar secret pehle hi commit ho chuka hai. Exposed credential ko revoke/rotate karna aur history cleanup ke appropriate process ko follow karna important hai.

24. Common Collaboration Mistakes

❌ Directly main par kaam karna

Feature work ke liye project policy ke according feature branch use karna safer workflow ho sakta hai.

❌ Long-lived branches

Bahut long time tak branch ko main se sync na karne par conflicts aur integration complexity badh sakti hai.

❌ Pull na karna

Outdated local branch se work karne par unnecessary conflicts aa sakte hain.

❌ Huge PR

Bahut large unrelated changes review ko difficult bana dete hain.

❌ Secrets commit karna

Credentials ko source code me store karna security risk hai.

❌ Force push on shared branch

Shared history disrupt ho sakti hai. Protected/shared branches par avoid karo.

❌ Conflict ko blindly resolve karna

“Ours”/“theirs” blindly choose karne ke bajay intended behavior samjho.

26. GitHub Collaboration Interview Questions

Q1. Git aur GitHub me difference?

Git distributed version control system hai; GitHub Git repositories ko host karne aur collaboration workflows jaise PR, review aur automation provide karne wala platform hai.

Q2. Pull Request kya hota hai?

PR proposed changes ko target branch me review/discussion/integration ke liye submit karne ka GitHub workflow hai.

Q3. Feature branch kyu use karte hain?

Feature work ko main/stable branch se isolate rakhne aur controlled integration ke liye.

Q4. git fetch aur git pull difference?

fetch remote updates ko local remote-tracking refs tak lata hai; pull fetch ke baad configured/selected integration operation karta hai.

Q5. Merge conflict kya hota hai?

Jab Git do change sets ko automatically combine nahi kar pata, usually overlapping incompatible changes ke case me, conflict generate hota hai.

Q6. Fork kya hota hai?

GitHub par repository ki account-level copy jisme contributor apne changes independently develop karke original project ko PR submit kar sakta hai.

Q7. Origin aur upstream?

Usually origin cloned/default remote hota hai; fork workflow me origin aapka fork aur upstream original repository hota hai.

Q8. Protected branch ka purpose?

Important branches par controlled integration, reviews, required checks aur restricted direct changes enforce karne ke liye.

Q9. PR me review feedback kaise handle karte ho?

Requested changes ko same source branch me commit karke push karte ho; existing PR update hota hai.

Q10. Rebase ke baad force push kyu required ho sakta hai?

Rebase commits ki history/hash change kar sakta hai. Remote branch history update karne ke liye force update required ho sakta hai; shared branches par avoid karna chahiye aur personal feature branch me --force-with-lease safer option hai.

Q11. GitHub collaboration me CI ka role?

PR/branch changes par automated tests, lint, build, security checks etc. run karke integration quality verify karna.

Q12. Secret commit ho gaya to?

Credential ko immediately revoke/rotate karna important hai; uske baad exposure/history cleanup project security process ke according handle kiya jata hai.
