1. GitHub Actions Artifacts

Simple definition: Workflow ke dauran generate hua output/file jise workflow run ke saath upload karke baad mein inspect, download, share ya next job mein use kiya ja sakta hai. Examples: dist/, JAR/WAR, test reports, coverage reports, ZIP/packages.

Real-life analogy

Factory mein raw material → production → finished product → warehouse. CI/CD mein source code → build/test → artifact.

Basic flow

Source
→
Build
→
Output
→
Upload
→
Download/Deploy

Upload artifact

- name: Build
  run: npm run build

- name: Upload build
  uses: actions/upload-artifact@v4
  with:
    name: web-build
    path: dist/
KeywordPurpose
upload-artifact@v4Files/directories upload.
nameArtifact identifier.
pathUpload source path.
download-artifact@v4Later job/step mein artifact retrieve.

Build → Deploy using artifact

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: app-build
          path: dist/

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: app-build
          path: dist/
      - run: echo "Deploy dist/ here"
BUILD JOB
source → build → dist/ → upload-artifact
                         ↓
                    GitHub Artifact
                         ↓
DEPLOY JOB ← download-artifact ← artifact
DevOps benefit: Build once, then same generated output ko later deployment stage mein use karo.

2. GitHub Actions Caching

Definition: Frequently reusable dependencies/files ko temporarily store karna taaki future runs mein same data ko scratch se dobara download/generate na karna pade.

Why cache?

CI mein dependencies repeatedly install hoti hain. npm, pip, Maven, Gradle jaise package ecosystems mein cache repeated network/download work ko reduce karke pipeline faster kar sakta hai.

First Run
→
Download
→
Save Cache
→
Next Run
→
Restore

Artifact vs Cache

ArtifactCache
Build/test output preserve/share.Repeated dependency/data work faster.
dist/, JAR, reports.npm/pip/Maven/Gradle dependency data.
Next job/release consume kar sakta hai.Performance optimization.
Deployable output ho sakta hai.Release source-of-truth nahi.
Golden rule: Artifact = output. Cache = speed optimization.

Explicit cache

- uses: actions/cache@v4
  with:
    path: some/cache/path
    key: ${{ runner.os }}-deps-${{ hashFiles('lockfile') }}
    restore-keys: |
      ${{ runner.os }}-deps-
KeywordMeaning
pathWhat to cache.
keyCache identity.
hashFiles()Lock/dependency file content se hash context.
restore-keysExact key miss hone par fallback prefixes.
runner.osOS-specific key.

Cache key concept

OS + runtime version + dependency lockfile state

Example:
ubuntu-latest-node-22-<lockfile-hash>

Lockfile change hone par hash change ho sakta hai, jisse new dependency cache context milta hai.

3. JavaScript / Node.js — Cache + Artifact

name: Node CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install
        run: npm ci

      - name: Test
        run: npm test

      - name: Build
        run: npm run build

      - name: Upload build
        uses: actions/upload-artifact@v4
        with:
          name: node-build
          path: dist/
  1. checkout source runner par.
  2. setup-node Node runtime.
  3. cache: npm npm cache.
  4. npm ci clean lockfile install.
  5. npm test validation.
  6. npm run build output.
  7. upload-artifact output preserve.

Explicit npm cache

- name: Get npm cache directory
  id: npm-cache
  run: echo "dir=$(npm config get cache)" >> "$GITHUB_OUTPUT"

- name: Cache npm
  uses: actions/cache@v4
  with:
    path: ${{ steps.npm-cache.outputs.dir }}
    key: ${{ runner.os }}-node-${{ hashFiles('package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-
Tip: setup-node ka built-in cache simple projects ke liye convenient hai; actions/cache custom paths/keys ke liye useful hai.

7. Job Concurrency in GitHub Actions

Definition: Concurrency control karta hai ki same logical group ke overlapping workflow/job runs ko kaise handle kiya jaye—especially duplicate runs ko cancel ya deployment ko serialize karna.

Why needed?

🚫 Duplicate CI

Old PR runs cancel.

💰 Resource saving

Unnecessary runners stop.

⚡ Latest code

Latest commit validation priority.

🔒 Deploy safety

Production deployments control.

Basic syntax

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
KeywordMeaning
concurrencyConcurrency policy.
groupLogical group identifier.
cancel-in-progressActive group run cancellation policy.

PR: latest run wins

name: PR CI

on:
  pull_request:

concurrency:
  group: pr-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test
Commit A → Run A ───────── X cancelled
Commit B → Run B ───── X cancelled
Commit C → Run C ─────────────→ active

Production: don't cancel active run

name: Production Deploy

on:
  push:
    branches: [ main ]

concurrency:
  group: production-deploy
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploy production"

Critical deployment mein active run ko automatically cancel na karna useful ho sakta hai; exact strategy application/environment requirements par depend karti hai.

Job-level concurrency

jobs:
  deploy:
    runs-on: ubuntu-latest
    concurrency:
      group: deploy-${{ github.ref }}
      cancel-in-progress: false
    steps:
      - run: echo "Deploy"

8. Multiple Concurrency Examples

Example 1 — Same branch CI

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

Same branch par new push old CI ko replace kar sakta hai.

Example 2 — Workflow + branch

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

Workflow identity + ref ko group mein include karke groups ko more specific banaya ja sakta hai.

Example 3 — PR number

concurrency:
  group: pr-${{ github.event.pull_request.number }}
  cancel-in-progress: true

Same PR ke runs cancel; different PRs independently run.

Example 4 — Environment-specific

on:
  workflow_dispatch:
    inputs:
      environment:
        required: true
        type: choice
        options: [staging, production]

concurrency:
  group: deploy-${{ inputs.environment }}
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploy ${{ inputs.environment }}"

Example 5 — Parallel checks → serialized deployment

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - run: echo lint

  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo test

  security:
    runs-on: ubuntu-latest
    steps:
      - run: echo security

  deploy:
    needs: [lint, test, security]
    runs-on: ubuntu-latest
    concurrency:
      group: production-deploy
      cancel-in-progress: false
    steps:
      - run: echo deploy
             ┌── Lint ────────┐
Push / PR ───┼── Test ─────────┼──→ Deploy
             └── Security ────┘       │
                 parallel       production group
Important: Group bahut broad hua to unrelated branches/environments unnecessarily block ho sakte hain. Group design deliberately karo.

13. Interview Questions

Q1. Artifact kya hai?

Workflow output ko upload/store/share karne ka mechanism.

Q2. Cache vs artifact?

Artifact output preservation; cache performance optimization.

Q3. Node cache?

actions/setup-node + cache: npm.

Q4. Python cache?

actions/setup-python + cache: pip.

Q5. Java Maven cache?

actions/setup-java + cache: maven.

Q6. hashFiles?

Dependency file changes ko cache key context mein include karne ke liye.

Q7. restore-keys?

Exact key miss par fallback prefixes.

Q8. Concurrency?

Overlapping runs/jobs ko group-based control karna.

Q9. cancel-in-progress true?

Latest PR/branch CI ko priority dene ke liye useful.

Q10. Production mein false?

Active deployment ko automatically cancel na karne ke liye; strategy environment requirements par depend karti hai.

Q11. Concurrency group?

Runs/jobs ka logical group identifier.

Q12. Artifact next job?

First job upload, later job download.

Q13. Cache ko release package use karna?

Nahi; cache optimization hai. Release output ke liye artifact/package/container registry use karo.
