1. Simple Workflow — First GitHub Actions Workflow

Goal: main par push hote hi workflow start ho aur runner par commands execute kare.

File location

.github/
└── workflows/
    └── simple.yml

Complete example

name: Simple Workflow

on:
  push:
    branches:
      - main

jobs:
  hello:
    runs-on: ubuntu-latest

    steps:
      - name: Say Hello
        run: echo "Hello from GitHub Actions"

      - name: Show Git version
        run: git --version

      - name: Show repository
        run: echo "Repository: $GITHUB_REPOSITORY"
git push

→

→

→
runner
→

Repository checkout kab chahiye?

Agar workflow ko source files build/test karni hain, normally checkout karo:

- uses: actions/checkout@v4

Sirf echo ya runner/GitHub environment inspect karne ke liye checkout har workflow mein required nahi.

Better CI example

name: Simple CI

on:
  push:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: List files
        run: ls -la
      - name: Check
        run: echo "CI is running successfully."

2. Schedule Workflow — Cron ke Through Automation

Schedule: Git event ka wait kiye bina workflow ko defined time par automatically run karna. Iske liye schedule + cron expression use hoti hai.

Basic example

name: Scheduled Workflow

on:
  schedule:
    - cron: '30 6 * * *'

jobs:
  daily-task:
    runs-on: ubuntu-latest
    steps:
      - name: Run scheduled task
        run: echo "Scheduled task executed."

Cron structure

┌──────── minute       0-59
│ ┌────── hour         0-23
│ │ ┌──── day of month 1-31
│ │ │ ┌── month        1-12
│ │ │ │ ┌ day of week  0-6
│ │ │ │ │
* * * * *
CronMeaning
0 * * * *Every hour at minute 0.
0 0 * * *Daily at 00:00 UTC.
30 6 * * *Daily at 06:30 UTC.
0 9 * * 1Every Monday 09:00 UTC.
0 0 1 * *First day of every month.
*/15 * * * *Every 15 minutes.
Timezone: GitHub Actions schedule UTC mein hota hai. IST = UTC + 5:30. Example: 06:30 UTC = 12:00 IST.

Scheduled + manual

name: Daily Maintenance

on:
  schedule:
    - cron: '0 3 * * *'
  workflow_dispatch:

jobs:
  maintenance:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Maintenance task"

schedule automatic run deta hai; workflow_dispatch manual testing/re-run ke liye useful hai.

Common use cases

🧹 Maintenance

Periodic cleanup.

🔐 Security

Scheduled checks/scans.

📊 Reports

Daily/weekly reports.

🔎 Monitoring

Periodic health/config checks.

3. How to Disable a Workflow

Disable: Workflow ko temporarily pause karna so that new trigger-based runs start na hon. Ye workflow file delete karne se different concept hai.

Method 1 — GitHub UI

  1. Repository open karo.
  2. Actions tab.
  3. Target workflow select karo.
  4. Available workflow controls mein Disable workflow choose karo.

Method 2 — Workflow ko remove/restore

git rm .github/workflows/deploy.yml
git commit -m "Remove deployment workflow"
git push origin main

Ye repository se definition remove karta hai; temporary pause ke liye UI disable zyada direct approach hai.

Method 3 — Manual-only workflow

name: Controlled Deployment

on:
  workflow_dispatch:

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Manual deployment"

Automatic push/PR trigger nahi hai; workflow manually run kiya ja sakta hai.

ApproachEffectUse
DisableExisting automation paused.Temporary pause.
Delete fileWorkflow definition removed.No longer needed.
Manual-onlyOnly manual trigger.Controlled deployment.
Trigger filtersSelected events/branches only.Scoped automation.
Important: Disabling a workflow and cancelling an already-running workflow run are separate operations.

4. Automate Angular Build Process

Goal: Push/PR → checkout → Node setup → npm ci → Angular build → artifact. Isse repetitive manual build process CI mein automate hota hai.

Typical project

my-angular-app/
├── src/
├── public/
├── angular.json
├── package.json
├── package-lock.json
└── tsconfig.json

Manual build

npm ci
npm run build

Workflow: .github/workflows/angular-ci.yml

name: Angular CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Build Angular application
        run: npm run build

      - name: Upload build artifact
        uses: actions/upload-artifact@v4
        with:
          name: angular-build
          path: dist/

package.json connection

{
  "scripts": {
    "start": "ng serve",
    "build": "ng build",
    "test": "ng test"
  }
}

npm run build actually package.json ka scripts.build execute karta hai.

Build + Test

name: Angular CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm test -- --watch=false
      - run: npm run build
Recommended learning pattern: PR par test/build validate karo; production deployment ko controlled CD stage/workflow mein rakho.

5. All Important Keywords — Deep Dive

name

name: Angular CI

UI label; execution logic change nahi karta.

on + event filters

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

Multiple event types combine kar sakte ho.

Path filters

on:
  push:
    paths:
      - 'frontend/**'
      - 'package.json'

Relevant files change hone par hi workflow run karne mein useful; monorepo mein helpful.

workflow_dispatch + inputs

on:
  workflow_dispatch:
    inputs:
      environment:
        description: Deployment environment
        required: true
        default: staging
        type: choice
        options:
          - staging
          - production

Manual workflow ko parameters dene ka structured method.

jobs + IDs

jobs:
  build:
    ...
  test:
    ...

Independent logical work units.

needs

deploy:
  needs: build
deploy:
  needs: [build, test]

Dependencies/order define karta hai.

runs-on

runs-on: ubuntu-latest

Runner OS/environment selection.

uses vs run

usesrun
Reusable Action.Shell command/script.
actions/checkout@v4npm ci

with

- uses: actions/setup-node@v4
  with:
    node-version: 22
    cache: npm

Action-specific inputs/configuration.

if

if: github.ref == 'refs/heads/main'

Conditional execution.

env

env:
  APP_ENV: production

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "$APP_ENV"

Expressions ${{ }}

run: echo "Branch: ${{ github.ref_name }}"

GitHub contexts/expression values evaluate karne ke liye.

Secrets

env:
  TOKEN: ${{ secrets.MY_TOKEN }}

Sensitive credentials ke liye. Secrets ko logs mein print mat karo.

permissions

permissions:
  contents: read

GITHUB_TOKEN access ko least privilege ke saath restrict karne mein useful.

Matrix

strategy:
  matrix:
    node: [20, 22]

runs-on: ubuntu-latest

Multiple versions/configurations par same tests.

timeout-minutes & continue-on-error

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 15
- run: ./optional-check.sh
  continue-on-error: true

Timeout runaway jobs ko limit karta hai; continue-on-error selected failure ko tolerated bana sakta hai—business logic ke according carefully use karo.

Interview Questions

Q1. Simple workflow ka basic structure?

name, on, jobs, runs-on, steps.

Q2. schedule ka use?

Cron-based automatic execution.

Q3. Cron timezone?

UTC.

Q4. workflow_dispatch?

Manual execution.

Q5. Disable vs delete?

Disable pause karta hai; delete/remove definition ko repository se hata deta hai.

Q6. Angular CI mein npm ci?

Lockfile-based clean/reproducible dependency installation ke liye.

Q7. Angular automation flow?

Trigger → checkout → Node → npm ci → npm run build → artifact.

Q8. uses vs run?

Action invocation vs shell command.

Q9. needs?

Job dependency/order.

Q10. paths?

Relevant file changes tak trigger scope karna.

Q11. CI/CD separate kyu?

Validation aur deployment ko independently control/security/troubleshoot karna easier.

Q12. Manual-only workflow?

Automatic triggers remove karke workflow_dispatch.
