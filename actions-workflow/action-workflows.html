1. GitHub Actions — Kya Hai, Kaise Kaam Karta Hai & Kyu Needed Hai?

Simple definition: GitHub Actions is GitHub ka automation and CI/CD platform hai. Iske through repository ke andar hone wale events—jaise push, pull_request, release, schedule, ya manual trigger—ke basis par automated tasks run karwa sakte ho.

GitHub Actions ko simple language mein samjho

Suppose tumne code GitHub par push kiya. Normally tumhe manually: build karna, tests run karna, Docker image banana, server par deploy karna aur notification bhejna pad sakta hai. GitHub Actions in steps ko automatically execute kar sakta hai.

GitHub Actions ki need kyu hoti hai?

⚙️ Automation

Repeated manual tasks ko automatically run karna.

🧪 Continuous Testing

Har push/PR par automated tests run karna.

🔨 Continuous Integration

New code ko automatically build aur validate karna.

🚀 Continuous Delivery

Validated application ko deployment process tak le jana.

🐳 Docker

Docker image build, tag aur registry push automate karna.

☁️ Cloud Deployment

AWS, Azure, GCP ya other environments ke deployment steps automate karna.

Real-life analogy

Restaurant analogy:

Customer order deta hai → order kitchen ko milta hai → ingredients prepare hote hain → food cook hota hai → quality check hota hai → waiter serve karta hai.

GitHub Actions mein: event → workflow → jobs → steps → validation/deployment. Har stage predefined instructions ke according automatically execute ho sakti hai.

2. GitHub Actions Workflow — Kya Hota Hai?

Definition: Workflow ek YAML file hoti hai jo define karti hai ki kab automation start hogi, kis runner/environment par chalegi, kaunse jobs run honge, aur har job ke andar kaunse steps execute honge.

Workflow file kaha hoti hai?

.github/
└── workflows/
    └── ci.yml

GitHub repository ke root ke andar .github/workflows/ directory mein YAML workflow files rakhi jati hain.

Workflow ki need kyu?

Agar automation rules scattered scripts mein rakhe hon, to team ke liye samajhna aur maintain karna difficult ho sakta hai. Workflow ek declarative definition deta hai: event aane par kya automation execute honi chahiye.

Workflow ka basic structure

name: CI

on:
  push:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Run tests
        run: npm test

Is example ko line-by-line samjho

LineMeaning

testJob ka identifier.
runs-onJob kis runner environment par execute hoga.

Workflow ke common triggers

3. Key Components of a GitHub Actions Workflow

Workflow ko deeply samajhne ke liye uske building blocks ko samjho: Workflow → Events → Jobs → Runner → Steps → Actions → Commands → Artifacts/Outputs → Secrets/Variables.

3.1 Workflow

Complete automation definition. Ek repository mein multiple workflows ho sakte hain.

.github/workflows/ci.yml
.github/workflows/deploy.yml
.github/workflows/security.yml

3.2 Events / Triggers — on

Event decide karta hai ki workflow kab start hoga.

on:
  push:
    branches: [ main ]

  pull_request:
    branches: [ main ]

  workflow_dispatch:
Important: Trigger ko “workflow ka first gate” samjho. Event match nahi hua to workflow normally start nahi hoga.

3.3 Jobs

Job ek logical unit of work hai. Ek workflow mein one or more jobs ho sakte hain. Jobs by default independent run kar sakte hain; dependencies define karke order bhi control kar sakte ho. 

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: npm ci
      - run: npm run build

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: npm test

3.4 Runner

Runner woh compute environment hai jahan job actually execute hoti hai. GitHub-hosted runners common operating systems ke environments provide karte hain; organizations self-hosted runners bhi use kar sakti hain. 

runs-on: ubuntu-latest

3.5 Steps

Steps job ke andar execution units hain. Ye order mein execute hote hain.

steps:
  - name: Checkout
    uses: actions/checkout@v4

  - name: Install dependencies
    run: npm ci

  - name: Test
    run: npm test

3.6 Actions — uses

Action reusable automation component hota hai. Example: repository checkout karne ke liye actions/checkout. 

- uses: actions/checkout@v4

Yaad rakho: uses reusable action ko call karta hai, jabki run shell command execute karta hai.

3.7 Shell Commands — run

- name: Check Node version
  run: node --version

- name: Run tests
  run: npm test

3.8 Dependencies — needs

Ek job ko dusri job ke successful completion ke baad run karwana ho to needs use kar sakte ho.

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Build"

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploy"

3.9 Environment Variables — env

env:
  NODE_ENV: production

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      APP_NAME: demo-app
    steps:
      - run: echo "$APP_NAME"

3.10 Secrets

Sensitive values—jaise cloud credentials, API tokens, deployment credentials—ko repository code mein hard-code nahi karna chahiye. GitHub Secrets/appropriate identity mechanisms ka use karo. 

env:
  API_TOKEN: ${{ secrets.API_TOKEN }}
Security rule: Passwords, private keys, cloud access keys aur tokens ko YAML file mein directly commit mat karo. Least privilege aur short-lived/managed credentials ko prefer karo.

3.11 Outputs

Ek step/job ka generated value next step/job ko pass karne ke liye outputs useful hote hain.

3.12 Artifacts

Build/test output ko workflow ke baad inspect ya download karne ke liye artifacts use kiye ja sakte hain, jaise test reports, binaries, build packages.

3.13 Conditions — if

if: github.ref == 'refs/heads/main'


Condition true hone par step/job execute ho sakta hai.



3.14 Matrix Strategy



Same tests ko multiple versions/operating systems par run karne ke liye matrix strategy useful hai.



strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    node: [20, 22]

runs-on: ${{ matrix.os }}

4. Workflow Execution Flow — Detailed

Core execution idea: Event trigger hota hai → GitHub workflow identify karta hai → run create hota hai → jobs schedule hote hain → runner provision/allocate hota hai → steps execute hote hain → logs/results generate hote hain → dependencies/conditions ke basis par next jobs run hote hain → workflow success/failure state par end hota hai.

Complete execution flow

┌───────────────────────┐ │ 1. Repository Event │ │ push / PR / manual │ └───────────┬───────────┘ │ v ┌───────────────────────┐ │ 2. Trigger Matching │ │ Does event match `on`?│ └───────────┬───────────┘ │ Yes v ┌───────────────────────┐ │ 3. Workflow Run │ │ GitHub creates run │ └───────────┬───────────┘ │ v ┌───────────────────────┐ │ 4. Job Scheduling │ │ dependencies/if check │ └───────────┬───────────┘ │ v ┌───────────────────────┐ │ 5. Runner │ │ environment selected │ └───────────┬───────────┘ │ v ┌───────────────────────┐ │ 6. Steps │ │ checkout → setup → │ │ install → test → build│ └───────────┬───────────┘ │ v ┌───────────────────────┐ │ 7. Logs / Outputs │ │ status + artifacts │ └───────────┬───────────┘ │ v ┌───────────────────────┐ │ 8. Next Job? │ │ needs / conditions │ └───────┬─────────┬─────┘ │ Yes │ No v v Next Job Workflow End │ v Deploy / Release

Step-by-step example

Step 1 — Developer pushes code

git add .
git commit -m "Add login feature"
git push origin main

Step 2 — GitHub receives the event

Repository ko push event milta hai. GitHub check karta hai ki kisi workflow ka trigger is event se match karta hai ya nahi.

Step 3 — Workflow starts

on:
  push:
    branches: [ main ]

Push agar main branch par hua hai, workflow eligible ho sakta hai.

Step 4 — Jobs are scheduled

GitHub workflow ke jobs ko evaluate karta hai. needs dependencies, if conditions aur strategy configuration execution order/eligibility ko affect kar sakte hain.

Step 5 — Runner executes a job

runs-on: ubuntu-latest

Selected runner par job ke steps execute hone lagte hain.

Step 6 — Repository checkout

- uses: actions/checkout@v4

Workflow environment mein repository content available karaya jata hai.

Step 7 — Environment setup

- uses: actions/setup-node@v4
  with:
    node-version: 22

Step 8 — Dependencies install

- run: npm ci

Step 9 — Tests run

- run: npm test

Agar test command non-zero exit status ke saath fail hota hai, default behavior mein affected step/job fail ho sakta hai, aur dependent jobs normally execute nahi karengi unless workflow logic explicitly allows otherwise.

Step 10 — Build

- run: npm run build

Step 11 — Deploy

deploy:
  needs: build
  runs-on: ubuntu-latest
  steps:
    - run: echo "Deploy application"

Parallel vs Sequential jobs

PatternExampleUse
Parallellint + test + securityIndependent checks ko faster run karna.
Sequentialbuild → deployDeploy ko build ke baad run karna.
Mixedlint/test parallel → package → deployReal CI/CD pipelines.
┌── Lint ───────┐ Push / PR ────────┼── Test ────────┼──> Build ──> Deploy └── Security ───┘ parallel sequential

Success and failure flow

✅ Success

Required steps pass → dependent jobs eligible → artifact/deployment can proceed.

❌ Failure

A required step fails → job generally fails → dependent jobs may be skipped unless conditions alter behavior.

⚠️ Conditional

if, needs, matrix and other workflow logic execution ko control kar sakte hain.

Complete Practical CI Workflow Example

name: Node CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test

      - name: Build application
        run: npm run build

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest

    steps:
      - name: Deployment placeholder
        run: echo "Deploy application here"

Practical Lab — Apna First GitHub Actions Workflow

Step 1 — Repository create/clone

git clone <your-repository-url>
cd your-repository

Step 2 — Workflow directory

mkdir -p .github/workflows

Step 3 — Workflow file

Create:

.github/workflows/hello.yml
name: Hello GitHub Actions

on:
  push:
    branches: [ main ]
  workflow_dispatch:

jobs:
  hello:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Show information
        run: |
          echo "Hello from GitHub Actions"
          echo "Repository: $GITHUB_REPOSITORY"
          echo "Branch/Ref: $GITHUB_REF"

      - name: Check system
        run: |
          uname -a
          git --version

Step 4 — Commit and push

git add .github/workflows/hello.yml
git commit -m "Add first GitHub Actions workflow"
git push origin main

Step 5 — GitHub par result dekho

  1. Repository open karo.
  2. Actions tab open karo.
  3. Hello GitHub Actions workflow select karo.
  4. Latest workflow run open karo.
  5. Job open karke individual step logs dekho.
Practice challenge: Workflow mein ek step add karo jo Node/Python version print kare, phir ek test command run karo, aur finally ek artifact upload karne ka experiment karo.

Interview Questions

Q1. GitHub Actions kya hai?

GitHub Actions GitHub ka automation/CI/CD platform hai jo repository events ke response mein workflows execute karta hai.

Q2. Workflow kya hota hai?

YAML-defined automation process jo trigger, jobs, runners aur steps define karta hai.

Q3. Workflow file kaha store hoti hai?

.github/workflows/ directory mein.

Q4. on ka kya purpose hai?

Workflow ko trigger karne wale events define karta hai.

Q5. Job aur step mein difference?

Job logical execution unit hai; step us job ke andar individual action/command hai.

Q6. uses aur run mein difference?

uses reusable action invoke karta hai; run shell command execute karta hai.

Q7. Runner kya hai?

Runner woh machine/environment hai jahan job ke steps execute hote hain.

Q8. needs ka use?

Job dependency define karne ke liye; dependent job required job ke completion ke baad eligible hoti hai.

Q9. Secrets kyu use karte hain?

Sensitive credentials ko workflow source code mein hard-code karne se bachane ke liye.

Q10. GitHub Actions CI/CD mein kaha fit hota hai?

Git repository events ko automated build, test, security, packaging, release aur deployment processes se connect karta hai.

Q11. Jobs parallel kab run kar sakti hain?

Jab unke beech dependency nahi ho aur workflow configuration unhe independently schedule karne de.

Q12. Workflow manually kaise run kar sakte hain?

workflow_dispatch trigger configure karke GitHub UI/API se manual execution enable ki ja sakti hai.
